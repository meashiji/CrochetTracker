# Database Schema + SQLModel Models — Plan Brief

> Full plan: `context/changes/db-schema-and-models/plan.md`

## What & Why

Stand up the complete database layer for CrochetTracker from scratch: six SQLModel entity models, an async Postgres engine, and Alembic migrations running automatically on every Fly.io deploy. This is F-01 — the prerequisite for every other slice on the roadmap. Nothing else can be built until the schema exists and the DB connection works.

## Starting Point

`pyproject.toml` has only FastAPI and uvicorn. `app/models/` and `app/routes/` are empty. Fly Postgres is already provisioned and `DATABASE_URL` is set as a Fly secret — the code layer is the only missing piece.

## Desired End State

Six tables exist in Fly Postgres, created by a clean Alembic migration that runs automatically before each deploy via `fly.toml`'s `release_command`. Any FastAPI route can open an async DB session via a `get_session` dependency injected by FastAPI.

## Key Decisions Made

| Decision | Choice | Why (1 sentence) | Source |
|---|---|---|---|
| DB driver | `asyncpg` (async) | FastAPI is async-native; blocking the event loop under concurrent HTMX taps risks breaching the 100ms NFR | Plan |
| RowState initialisation | Eager (pre-create on paste) | Simplifies FR-007 "jump to first unmarked row" query — no LEFT JOIN needed | Plan |
| Pattern text storage | Both (raw text + parsed rows) | Raw text enables FR-004 boundary re-adjustment without re-pasting | Plan |
| User scope in F-01 | Minimal (id, email, created_at) | Auth fields are F-02's domain; keeping them separate makes each foundation independently deployable | Plan |
| Migration execution | Fly `release_command` | If a migration fails, the old version keeps running — safer than on-startup, no manual step | Plan |

## Scope

**In scope:** sqlmodel/asyncpg/alembic deps; `app/config.py`; `app/db.py`; six model files under `app/models/`; Alembic init + async `env.py`; initial autogenerated migration; `fly.toml` `release_command`.

**Out of scope:** Auth fields on User (F-02), route handlers (S-01+), seed data, RowState record creation (S-01 paste handler).

## Architecture / Approach

```
Fly Postgres (provisioned)
    │ DATABASE_URL secret
    ▼
app/config.py  ── normalises postgres:// → postgresql+asyncpg://
    │
app/db.py      ── create_async_engine(pool_size=3) + async_sessionmaker
    │              get_session() FastAPI dependency
    ▼
app/models/    ── 6 SQLModel table=True models
    │              SQLModel.metadata (Alembic's source of truth)
    ▼
alembic/env.py ── asyncio runner → alembic upgrade head
    │
fly.toml       ── [deploy] release_command = "alembic upgrade head"
```

## Phases at a Glance

| Phase | What it delivers | Key risk |
|---|---|---|
| 1. Dependencies + DB engine | pyproject.toml updated; `app/config.py` + `app/db.py` working | `postgres://` → `asyncpg://` URL transform must happen before engine creation |
| 2. SQLModel models | 6 entity models importable; all appear in `SQLModel.metadata` | `expire_on_commit=False` on sessionmaker; `UniqueConstraint` via SQLAlchemy import |
| 3. Alembic + migration + Fly | Migration applied; `fly deploy` runs it automatically | `env.py` must import all models before setting `target_metadata`; asyncio runner required for asyncpg |

**Prerequisites:** Fly Postgres provisioned ✓, `DATABASE_URL` Fly secret set ✓
**Estimated effort:** ~1 focused session (2–3 hours) across 3 phases

## Open Risks & Assumptions

- SQLModel with Python 3.14 — very new Python version; if import errors appear, `from __future__ import annotations` at the top of model files is the first fix to try
- Alembic autogenerate may miss `UniqueConstraint` on multi-column constraints if `__table_args__` is not set correctly — verify the generated migration before running it

## Success Criteria (Summary)

- `uv run alembic upgrade head` applies cleanly; `downgrade -1` reverts; upgrade again re-applies
- `fly deploy` log shows release_command exit 0
- `psql \dt` via `fly proxy` lists all six tables with the correct structure
